# Адаптация ALT Linux p11 для Репки Pi 4

По предоставленному техническому отчёту локального анализа студенческого проекта [repka-pi4-kiosk](https://github.com/maksim4pathy/repka-pi4-kiosk), срез исходников до коммита `652169033c429ed1924a21b4108234f6a68624c4`, отчёт от 17 ноября и эксплуатационный срез от 22 ноября 2026 года. История содержит изменения от имени Maksim Sobolivsky и Maxim; распределение задач не указано. Исходный репозиторий не удалось повторно открыть удалённо; сведения ниже основаны на предоставленном отчёте.

## Стенд и исходная проблема

Repka Pi 4 Optimal 1.1, Allwinner H6, четыре Cortex-A53, 2 ГБ RAM. Исходная система — ALT Workstation 11.2 (Prometheus) на SD. Ветка p11 — источник пакета ядра kernel-image-repka4; полный список репозиториев исходной системы не зафиксирован.

На исходном ядре 6.12.94 не работал Ethernet и не определялась eMMC. По отчёту причина связана с отсутствием поддержки AC200 EPHY и совместимости allwinner,sun50i-h6-emmc в sunxi-mmc. Студенты подобрали готовое вендорное ядро из p11: kernel-image-repka4 6.6.44-alt2_3.git4bdc0a7. После установки появился end0 (dwmac-sun8i и AC200 EPHY, 100 Мбит/с, полный дуплекс) и накопитель mmcblk2 ёмкостью 28,9 ГиБ. Также отмечена доступность HDMI, температурных зон, Bluetooth, I²C и звука.

## Перенос системы на eMMC

1. Установили вендорное ядро на исходную систему SD.
2. Подготовили FAT-раздел BOOT (~241 МиБ) и ext4 altroot (~28,7 ГиБ) на eMMC, с отдельными UUID.
3. Записали готовый U-Boot 2020.04-rc3 с SPL из /usr/share/u-boot/repka_pi4/ на eMMC со смещением 8 КиБ.
4. Перенесли около 12 ГБ системы через rsync -aHAX --numeric-ids с сохранением атрибутов.
5. Настроили extlinux с реальными путями к ядру, initrd, каталогу DTB соответствующей версии и root=UUID. Штатные символьные ссылки не работали с данным U-Boot. Перенесли флаг загрузки на корневой раздел и отключили EFI-заглушку переименованием BOOTAA64.EFI.
6. Проверили загрузку без SD через UART (115200, 8N1), uname -r и findmnt -no SOURCE /.

Это описание переноса существующей системы, а не рецепт сборки образа с нуля. Перед любыми операциями записи нужно определить целевой носитель по lsblk и сохранить резервную копию; нумерация накопителей относится к конкретному стенду.

## Серверный профиль

Настроили multi-user.target, сохранили sshd, httpd2, NetworkManager и chronyd. Отключили GDM и ненужные службы; пакеты GNOME/Xorg сохранили для отката. Ethernet — основной маршрут с метрикой 100, Wi-Fi DHCP — резервный с метрикой 600. Исходная SD оставлена для аварийной загрузки.

## Информационный киоск

- Xorg через xinit, дисплей :0, tty1; Chromium в режимах --kiosk и --app. Геометрия определяется xrandr с резервным xdpyinfo. URL задаётся в /etc/kiosk/url.
- Установщик поддерживает непривилегированного пользователя, отдельные --start и --enable, systemd-службу с конфликтом getty@tty1 и восстановлением консоли после остановки.
- Локальный HTML содержит поиск преподавателей, выбор времени консультации, экранную клавиатуру и подтверждение. Бронирования пока живут в памяти страницы; постоянного серверного хранилища нет.
- Голосовой ввод: локальный Vosk HTTP API на 127.0.0.1:2700, GET /health и POST /listen; USB-микрофон через ALSA/arecord, русская модель. Настройки в /etc/vosk-listener.env.
- Cage/Wayland отложен после SIGSEGV при подключении Chromium. Рабочий вариант — Xorg; HDMI 1920×1080. Проблему неполного экрана решили передачей фактической геометрии окна. Встроенное аудио не обеспечило нужный режим записи, использовали USB-микрофон.

## Подтверждённые результаты и границы вклада

На одном стенде подтверждены загрузка с eMMC без SD, ядро 6.6.44-repka4-alt2_3.git4bdc0a7, Ethernet, SSH, HTTP 200, отсутствие упавших systemd-юнитов, ручной запуск киоска и работа локального голосового сервиса. Срез от 22 ноября фиксирует выключенный автозапуск киоска и включённый автозапуск Vosk.

Студенческий вклад — диагностика аппаратной совместимости, подбор и интеграция готовых компонентов ядра и загрузчика, перенос системы, настройка служб и сети, собственные установщики, диагностика, интерфейс и голосовой сервис. Исходники ядра и U-Boot, патчи драйверов, DTS/DTB и свидетельства самостоятельной пересборки этих компонентов в предоставленном отчёте отсутствуют. Готовый образ и рецепт rootfs с нуля не представлены.

## Использование в Local-LLM-servers

Студенческая разработка даёт основу лёгкого терминала ALT Linux: браузерный интерфейс, локальный голосовой ввод, сетевое управление. Ресурсоёмкая генерация выполняется на внешних GPU-серверах. В нашем проекте сетевой доступ Репки к Open WebUI, авторизация и генерация токенов уже проверены отдельно; полная интеграция в интерфейс консультаций не подтверждена. Следующие этапы — подключение backend киоска к LLM API, безопасная передача данных, постоянное хранилище бронирований, автоматизация тиражирования. Не требуется развёртывать большую LLM на самой Репке.
